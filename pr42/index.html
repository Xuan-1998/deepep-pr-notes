DeepEP PR 42, explained

amazon-contributing/DeepEP#42, head b9a76ff on main c81a983. Every code link below points at the head commit.

The PR changes how the unordered combine sends its scale-out (rail) traffic, and it adds the host settings that this needs. It has five commits. This page explains four of them in detail. The middle commit in the diagram below, 472847a (the forward list as two FIFOs), was reviewed earlier and is not covered here. It only appears where the others depend on it.

Section 0 lists my review comments on those four commits: the line to comment on, the text, and the evidence. Sections 1 to 8 explain the code they refer to.

1. The five commits

2. Who posts the combine's scale-out puts

In the unordered combine, each forward warp owns one channel. It reduces tokens from the scale-up buffers and writes them into the scale-out send buffer. It then hands a descriptor (send pointer, receive pointer, bytes, destination node) to the proxy warp through a small ring in shared memory. The proxy warp turns descriptors into GIN puts on the rail. PR 42 changes how the proxy warp does that, and who waits for the incoming puts.

3. One proxy round

A round reads a snapshot of all rings first, and it posts only what that snapshot holds. The lane posts each descriptor one step late, so it knows the next descriptor's destination before it decides whether the current put rings the doorbell.

4. Worked example: one channel, two remote nodes, batch 6

Before the replay loop, each forward warp scans its forward list and counts the slots it owes every node. It then counts each destination down as it records slots. A batch is handed to the proxy when it holds kBatchSize slots, or when its destination reaches zero. When the total for all remote nodes reaches zero, the warp sets its ring's done flag.

The pre-scan and the replay use the same slot rule. Without multiple reduction, a token gives one slot per valid top-k entry (expanded layout) or per distinct scale-up rank. With multiple reduction, a token gives one slot. A mismatch would change the number of puts, and then the receiver's count.

5. GIN contexts, data QPs and the sharing mode

num_allocated_qps is the GIN context count n. Context 0 carries the notify barrier, contexts 1 to n - 1 are data QPs. The provider budget is 256 units per GPU, and a context costs 2 units plus 1 per indexed signal, so each context gets (256 - 2n) / n signals. A kernel on s SMs owns its QPs when s ≤ n - 1. Otherwise all SMs share all data QPs.

The combine proxy posts on its SM's first QP only (channel 0's QP). It uses THREAD mode when the SM owns that QP and the NCCL is 2.32.6 or later. On shared QPs it uses the mapped GPU mode. The dispatch spreads its channels over all of the SM's QPs.

Fewer signals per context mean fewer parts or fewer channels

The dispatch needs one signal per (channel on a QP) per part. compute_part_allocation first lowers the parts (4 at most), then the channels per SM, until channels per QP x parts fits the signals. With 41 contexts a QP has 4 signals, so an SM that owns one QP keeps at most 4 channels with 1 part. That limit applies with overlap on (7 channels) as well.

The rail cap

Every context also needs one signal per peer node on the rail. So a rail of R nodes fits at most 256 / (R + 1) contexts, and buffer creation clamps the request to that, with a warning.

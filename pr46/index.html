4. gin_config on the two calls (R1)

create_dev_comm can run twice in one process: once from the constructor, and once more for gin_dev_comm when the constructor skipped GIN (a single NVLink domain whose PP or Engram later asks for it, d779c47). The NOTES comment describes what the first call leaves behind.

main c81a983 (nccl.cu L144-L256)PR 5492668 (nccl.cu L146-L196, gin_unordered.hpp L28-L77)
Call 1, no GINThe unordered block is inside if (with_gin and not gin_disabled) (L162), so nothing touches gin_config or clamps num_allocated_qps. At the bottom, 0 becomes the default count.configure_unordered_gin runs (L176-L179): clamps num_allocated_qps into [2, 17] with a [WARN] if it moved (L35-L41), sets gin_context_cnt (L44), returns before the budget (L45-L46). gin_indexed_signals_cnt stays 0.
Call 2, with GINThe block runs: clamp, make_gin_resources, the signal assert, num_allocated_qps = gin_context_cnt (L172-L203).configure_unordered_gin runs again: the clamp is a no-op on an in-range value, make_gin_resources fills the budget (L56-L58), the assert follows (L63-L65).
End stateThe same context count and signal budget on both sides. The one difference is on call 1: the PR clamps and may warn where main did nothing, so a run that never asks for GIN with a value outside [2, 17] now sees the clamp.

"has no signal budget" in the new comment is this zero gin_indexed_signals_cnt after call 1. A reworded version: "a second call (for gin_dev_comm) only happens when the constructor skipped GIN; that first call ran configure_unordered_gin without GIN, which clamps num_allocated_qps and sets the context count but returns before the signal budget, so this call recomputes both and ends with the values the constructor produced before the gate existed."
